设计模式是在某种场合下**对某个问题的一种解决方案，作用是让人们写出可复用和可维护性高的程序，千万不要为了使用设计模式而刻意使用设计模式**，换言之，设计模式一定要结合场景，脱离了场景谈模式，无异于空谈，防止调入“锤子理论”当我们有了一把锤子，看什么都是钉子。拿足球比赛的例子来说，我们的目标只是进球..

绝大部分设计模式的实现都离不开**多态性的思想**。实际含义是：同一操作作用于不同的对象上面，可以产生不同的解释和不同的执行结果。

## 一、各种模式

### 1.1、单例模式

核心是**确保只有一个实例，并且能够全局访问，用途已经很明显了（防止重复创建对象），不再赘述**

以往页面中添加元素为例：

```js
function CreateDiv(html) {
  this.html = html;
  this.init();
}

CreateDiv.prototype.init = function () {
  let div = document.createElement("div");
  div.innerHTML = this.html;
  document.body.appendChild(div);
};
// 闭包
let ProxySingleCreateDiv = (function () {
  let instance;
  return function (html) {
    // 判断有没有实例，如果有就直接返回实例，没有就创建实例
    if (!instance) {
      instance = new CreateDiv(html);
    }
    return instance;
  };
})();

let a = new ProxySingleCreateDiv("hello");// 可能更像实例一点吧
// 也可以这样：
// let a = ProxySingleCreateDiv("world");

```

### 1.2、策略模式（重点）

**用途：解决多重判断的问题（避免写各种if-else）**，不同策略放进一个对象中形成一个策略对象“{...}”，根据情况调用不同策略。

还是以发奖金问题为例：

> “ 绩效为 S 的人年 终奖有 4 倍工资，绩效为 A 的人年终奖有 3 倍工资，而绩效为 B 的人年终奖是 2 倍工资。假设财 务部要求我们提供一段代码，来方便他们计算员工的年终奖。 ”

我们很自然的想到会封装一个函数：里面有两个参数——等级level和工资salary，素以就有了：

```js
function calculateBonus(level, salary) {
  if (level === "S") {
    return salary * 4;
  } else if (level === "A") {
    return salary * 3;
  } else if (level === "B") {
    return salary * 2;
  }
}

```

很明显上述的实现方法有问题，如果将来有其他等级呢，是不是还得改代码——又新增一个判断语句，这样显然不够优雅。

但是如果我们使用策略模式呢，我们把上面的一个个计算奖金的**不同策略放进一个对象中形成一个策略对象**，然后根据情况调用不同的策略即可：

```js
// 策略对象
var strategies = {
  // 策略一
  S: function (salary) {
    return salary * 4;
  },
  // 策略二
  A: function (salary) {
    return salary * 3;
  },
  // 策略三
  B: function (salary) {
    return salary * 2;
  },
};
// 使用策略
var calculateBonus = function (level, salary) {
  return strategies[level](salary);
};

```

要使用策略模式，必须了解所有的`strategy`，必须了解各个`strategy` 之间的不同点， 这样才能选择一个合适的 `strategy`。

### 1.3、 代理模式

**用途**：代理模式是为一个对象提供一个代用品或占位符，以便控制对它的访问；

在javaScript中最常见的是**虚拟代理和缓存代理**，下面对两种情况进行说明：

1.  **虚拟代理：典型的应用场景是图片预加载**（ 常见的做法是先用一张 loading 图片占位，然后用异步的方式加载图片，等图片加载好了再把它填充到 img 节点里）。

```js
var myImage = (function(){ 
 var imgNode = document.createElement( 'img' ); 
 document.body.appendChild( imgNode ); 
 return { 
 setSrc: function( src ){ 
 imgNode.src = src; 
 } 
 } 
})(); 
var proxyImage = (function(){ 
 var img = new Image; 
 img.onload = function(){ 
 myImage.setSrc( this.src ); 
 } 
 return { 
 setSrc: function( src ){ 
 myImage.setSrc( 'file:// /C:/Users/svenzeng/Desktop/loading.gif' ); 
 img.src = src; 
 } 
 } 
})(); 
proxyImage.setSrc( 'http:// imgcache.qq.com/music/photo/k/000GGDys0yA0Nk.jpg' ); 

```

2.  **缓存代理**： 可以为一些开销大的运算结果提供暂时的存储，在下次运算时，如果传递进来的参数跟之前一致，则可以直接返回前面存储的运算结果。

```js
var mult = function(){ 
 console.log( '开始计算乘积' ); 
 var a = 1; 
 for ( var i = 0, l = arguments.length; i < l; i++ ){ 
 a = a * arguments[i]; 
 } 
 return a; 
}; 
mult( 2, 3 ); // 输出：6 
mult( 2, 3, 4 ); // 输出：24

var proxyMult = (function(){ 
   var cache = {}; 
   return function(){ 
       var args = Array.prototype.join.call( arguments, ',' ); 
       // 如果满足条件说明曾经计算过，直接使用计算过的数据
       if ( args in cache ){ 
         return cache[ args ]; 
       } 
     // 添加属性，以便以后碰见一样的了，直接使用缓存中的数据
       return cache[ args ] = mult.apply( this, arguments ); 
   } 
})(); 

proxyMult( 1, 2, 3, 4 ); // 输出：24 
proxyMult( 1, 2, 3, 4 ); // 输出：24 
```

> 虽然代理 模式非常有用，但我们在编写业务代码的时候，往往不需要去预先猜测是否需要使用代理模式。 当真正发现不方便直接访问某个对象的时候，再编写代理也不迟

此外还有防火墙代理，保护代理等，不常用所以在这里不再赘述。

### 1.4、迭代器模式

**定义**：是指提供一种方法顺序访问一个聚合对象中的各个元素，而又不需要暴露该对象 的内部表示。 其实说白了就是JS中的`Array.prototype.forEach`，内部已经有实现，不再赘述。

### 1.5、发布-订阅模式（重点）

**定义**：又叫观察者模式， 当一个对象的状态发生改变时，所有依赖于它的对象都将得到通知。 在 JavaScript 开发中，我们一般**用事件模型来替代传统的发布—订阅模式** 。

**优点**：发布者和订阅者松耦合。

**缺点**：你订阅的“事件”不一定发生，订阅者始终在内存中

1.  DOM事件

```js
document.body.addEventListener('click',function(){
  alert(1)
})
```

`document.body`订阅了`click`事件，当点击事件发生的时候就会执行`function`；

2.  **自定义事件**

自己实现一个发布-订阅模式~，在实现之前要搞清楚三个问题：

1.  首先要指定好谁充当发布者（比如售楼处）；
2.  然后给发布者添加一个缓存列表，用于存放回调函数以便通知订阅者（售楼处的花名册）；
3.  最后发布消息的时候，发布者会遍历这个缓存列表，依次触发里面存放的订阅者回调函 数（遍历花名册，挨个发短信）。

```js
let salesOffices = {
  clientList: [], // 存放订阅者的回调函数
  listen(fn) {
    // 增加订阅者
    this.clientList.push(fn);
  },
  // 遍历触发曾经缓存的函数
  trigger() {
    for (let i = 0; i < this.clientList.length; i++) {
      var fn = this.clientList[i];
      fn.apply(this, arguments);
    }
  },
};

salesOffices.listen(function (price, squareMeter) {
  console.log(`价格${price}，面积${squareMeter}㎡`);
});
salesOffices.listen(function (price, squareMeter) {
  console.log(`价格是${price}，面积是${squareMeter}㎡`);
});
salesOffices.trigger(1000000, 90);
salesOffices.trigger(12000, 100);
```

实现了，但是你会发现一个问题，订阅者接收到了发布者的每一个消息，这显然不太合理，更合理的情况应该是对订阅者进行分类，也就是说要增加一个参数key来标示某类订阅者的集合，所以就有了：

```js
let salesOffices1 = {
  clientList1: {}, // 存放各种订阅者的函数
  listen(key, fn) {
    //  如果这一类没人定阅，新建这一类
    if (!this.clientList1[key]) {
      this.clientList1[key] = [];
    }
    // 增加订阅者
    this.clientList1[key].push(fn);
  },
  // 触发
  trigger() {
    let key = Array.prototype.shift.call(arguments); // 取出订阅类型key,取出第一个参数
    let fns = this.clientList1[key]; // 拿到该类订阅者所缓存的回调函数列表
    for (let i = 0; i < fns.length; i++) {
      fns[i].apply(this, arguments);
    }
  },
};

// 这有没有很像点击事件的格式？dom.addEventListener('click',func(){})
salesOffices1.listen("type1", function (price, squareMeter) {
  console.log(`价格${price}，面积${squareMeter}㎡`);
});
salesOffices1.listen("type1", function (price, squareMeter) {
  console.log(`价格${price}，面积${squareMeter}㎡`);
});
salesOffices1.listen("type2", function (price, squareMeter) {
  console.log(`价格是${price}，面积是${squareMeter}㎡`);
});

salesOffices1.trigger("type1", 1500000, 120);
salesOffices1.trigger("type2", 1800000, 145);
```

但是还有一个问题，怎么取下订阅呢，我们给上述对象添加remove方法

```js
let salseOffices = {
  // ...
   // 取消订阅
  remove(key, fn) {
    //  取消订阅又好几种取消方式，首先如果只传key，是把所有的这一类都取消了，如果穿fn，那么只该类中的一个
    let fns = this.clientList1[key];
    // 表示该类下没有任何的订阅者，因为根本没有创建该类
    if (!fns) {
      return false;
    }
    // 不传具体的回调函数，则key对应的所有消息订阅都要取消
    if (!fn) {
      fns && (fns.length = 0);
    } else {
      // 反向遍历清空
      for (var j = fns.length - 1; j >= 0; j--) {
        let _fn = fns[j];
        if (fn === _fn) {
          fns.splice(j, 1);
        }
      }
    }
  },
}

salesOffices1.remove("type1");
salesOffices1.trigger("type1", 1800000, 160);// 没触发
salesOffices1.trigger("type2", 2000000, 180);// 价格是2000000，面积是180㎡
```

上面的代码都是先订阅然后发布，**但是有没有可能先发布再订阅呢？**有没有这样的场景呢，当然有！比如当你微信离线（没有订阅者）时别人给你发的消息（发布了），你登录后能自动接收到（有订阅者还能接收到信息）

​  

**为了满足这个需求，我们要建立一个存放离线事件的堆栈，当事件发布的时候，如果此时还 没有订阅者来订阅这个事件，我们暂时把发布事件的动作(就是上面的**`salesOffices1.listen`**)包裹在一个函数里**，这些包装函数将被 存入堆栈中，等到终于有对象来订阅此事件的时候，我们将遍历堆栈并且依次执行这些包装函数， 也就是重新发布里面的事件 。

### 1.6、命令模式

**分析：**

1.  命令模式的本质是对命令进行封装，将**发出命令的责任和执行命令的责任分割开**。
2.  每一个命令都是一个操作：请求的一方发出请求，要求执行一个操作；接收的一方收到请求，并执行操作。

**优点：**

1.  降低对象间的耦合度
2.  添加新命令更加方便

### 1.7 、组合模式

**定义**： 用小的子对象来构建更大的对象，而这些小的子对象本身也许是由更 小的“孙对象”构成的

**用途**：

1.  表示树形结构
2.  利用对象多态性**统一对待**组合对象（有叶子节点）和单个对象（不再区分组合对象和单个对象）。

![image.png](https://cdn.nlark.com/yuque/0/2022/png/1528528/1650616805381-f7f36dff-efd7-42be-be40-95e722a280ba.png)

**注意：**

组合模式除了要求**组合对象和叶对象拥有相同的接口**之外， 还有一个必要条件，就是对一组叶对象的操作必须具有一致性。

例子：给每个员工发放过节费1000，要知道员工是有部门（组合对象）的 ，如果每个员工过节费不一样，那就不能用组合模式。

### 1.8、职责链模式（重点）

**定义：** 使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间 的耦合关系，将这些对象连成一条链，并沿着这条链传递该请求，直到有一个对象处理它为止 。

> 为啥叫“有机会”呢，是因为说不定在这个对象就处理好了，如果处理不好就到下个对象

![image.png](https://cdn.nlark.com/yuque/0/2022/png/1528528/1650681385473-adcead0d-9151-4f3c-a27c-5d327e2f1a6c.png)

**举例**：上公交车传递钱给售票员，考试传纸条等。

**用途**：从定义就 可以看出这种模式主要用来处理复杂的关系的（常常会用到嵌套的`if-else`语句）

**优点**： **解耦了请求发送者和 N 个接收者之间的复杂关系**（由于关系复杂可能需要各种嵌套`if-else`），由于不知道链中的哪个节点可以处理你发出的请求，所以你只需把请求传递给第一个节点即可**。** **链中的节点对象可以灵活地拆分重组**。增加或者删除一个节 点，或者改变节点在链中的位置都是轻而易举的事情。

**缺点**：节点可能过长，可能造成性能损失

> 这种模式使程序中多了一些节点对象，可能在某一次的请求传递过程中，大部分 节点并没有起到实质性的作用，它们的作用仅仅是让请求传递下去，从性能方面考虑，我们要避免过长的职责链带来的性能损耗

  

举个例子，有这么个场景：

> 假设我们负责一个售卖手机的电商网站，经过分别交纳 500 元定金和 200 元定金的两轮预定
> 
> 后（订单已在此时生成），现在已经到了正式购买的阶段。
> 
> 公司针对支付过定金的用户有一定的优惠政策。在正式购买后，已经支付过 500 元定金的用
> 
> 户会收到 100 元的商城优惠券，200 元定金的用户可以收到 50 元的优惠券，而之前没有支付定金
> 
> 的用户只能进入普通购买模式，也就是没有优惠券，且在库存有限的情况下不一定保证能买到

约定参数——

1.  orderType：表示订单类型（定金用户或者普通购买用户），code 的值为 1 的时候是 500 元 定金用户，为 2 的时候是 200 元定金用户，为 3 的时候是普通购买用户。
2.  pay：表示用户是否已经支付定金，值为 true 或者 false, 虽然用户已经下过 500 元定金的 订单，但如果他一直没有支付定金，现在只能降级进入普通购买模式。
3.  stock：表示当前用于普通购买的手机库存数量，已经支付过 500 元或者 200 元定金的用 户不受此限制。

​  

封装函数——

```js

function order(orderType, pay, stock) {
  if (orderType === 1) {
    if (pay) {
      console.log("500元定金，得到100元优惠券");
    } else {
      if (stock > 0) {
        console.log("没有优惠券，普通购买");
      } else {
        console.log("手机库存不足");
      }
    }
  } else if (orderType === 2) {
    if (pay) {
      console.log("200元定金，得到100元优惠券");
    } else {
      if (stock > 0) {
        console.log("没有优惠券，普通购买");
      } else {
        console.log("手机库存不足");
      }
    }
  } else {
    if (stock > 0) {
      console.log("没有优惠券，普通购买");
    } else {
      console.log("手机库存不足");
    }
  }
}
```

太多的嵌套，稍微条件一变函数就得变（比如又新增300元的定金，优惠券80呢，是不是又一个if-else），而且可阅读性比较差，那么使用责任链呢？

```js
// 定义三个函数分别处理定金500的情况，定金200的情况和无定金的情况，参数和上面的一样

/**
 *
 * @param {*} orderType 1：00定金的用户，2：200定金的用户，3：无定金
 * @param {*} pay true：已支付，false：未支付
 * @param {*} stock 库存数量
 */

// 500元定金
function order500(orderType, pay, stock) {
  if (orderType === 1 && pay) {
    console.log("500元定金，得到100元优惠券");
  } else {
    order200(orderType, pay, stock);
  }
}

// 200元定金
function order200(orderType, pay, stock) {
  if (orderType === 2 && pay) {
    console.log("200元定金，得到50元优惠券");
  } else {
    orderNormal(orderType, pay, stock);
  }
}
// 无定金
function orderNormal(orderType, pay, stock) {
  // 由于根本没有定金，也就没有了orderType, pay存在的意义，所以其实可以省略，但为了保持一致性，暂且放在这里吧
  if (stock > 0) {
    console.log("没有优惠券，普通购买");
  } else {
    console.log("手机库存不足");
  }
}

order500(1, true, 300); // 500元定金，得到100元优惠券
order500(1, false, 300); // 没有优惠券，普通购买
order500(2, true, 300); // 200元定金，得到50元优惠券
order500(2, false, 300); // 没有优惠券，普通购买
order500(3, false, 300); // 没有优惠券，普通购买
order500(3, true, 300); // 没有优惠券，普通购买

```

虽然也实现了，但就拿`order500`函数而言，其内部和`order200`强绑定，那如果将来再来一个定金300优惠80呢，还得改这个函数，能不能解除这个耦合关系呢？当然是可以的——

我们约定，如果某个节点不能处理请求，则返回一个特定的字符串 'nextSuccessor'来表示该请求需要继续往后面传递，需要对上述函数进行改造——

```js
/**
 *
 * @param {*} orderType 1：00定金的用户，2：200定金的用户，3：无定金
 * @param {*} pay true：已支付，false：未支付
 * @param {*} stock 库存数量
 */

// 500元定金
function flexOrder500(orderType, pay, stock) {
  if (orderType === 1 && pay) {
    console.log("500元定金，得到100元优惠券");
  } else {
    return "nextSuccessor";
  }
}

// 200元定金
function flexOrder200(orderType, pay, stock) {
  if (orderType === 2 && pay) {
    console.log("200元定金，得到50元优惠券");
  } else {
    return "nextSuccessor";
  }
}
// 无定金
function flexOrderNormal(orderType, pay, stock) {
  // 由于根本没有定金，也就没有了orderType, pay存在的意义，所以其实可以省略，但为了保持一致性，暂且放在这里吧
  if (stock > 0) {
    console.log("没有优惠券，普通购买");
  } else {
    console.log("手机库存不足");
  }
}

// 我们定义一个构造函数,将上述函数包装成处理节点
function FlexChain(fn) {
  this.fn = fn;
  this.successor = null; // 表示下一个处理节点
}

// 确定下一个处理的节点
FlexChain.prototype.nextSuccessor = function (successor) {
  this.successor = successor; //
};

// 在某一节点的处理
FlexChain.prototype.passRequest = function () {
  let result = this.fn.apply(this, arguments); // 拿到在该节点下处理的结果
  if (result === "nextSuccessor") {
    // 让下一个节点对应的函数进行处理这条订单，条件都一样
    this.successor &&
      this.successor.passRequest.apply(this.successor, arguments);
  }
  return result;
};

//将上述函数包装成责任链节点
let flexChain500 = new FlexChain(flexOrder500);
let flexChain200 = new FlexChain(flexOrder200);
let flexChainNormal = new FlexChain(flexOrderNormal);

// 指定责任链节点执行顺序
flexChain500.nextSuccessor(flexChain200);
flexChain200.nextSuccessor(flexChainNormal);

// 执行
flexChain500.passRequest(1, true, 300); //500元定金，得到100元优惠券
flexChain500.passRequest(1, false, 300); // 没有优惠券，普通购买
flexChain500.passRequest(2, true, 300); // 200元定金，得到50元优惠券
flexChain500.passRequest(2, false, 300); // 没有优惠券，普通购买
flexChain500.passRequest(3, true, 300); // 没有优惠券，普通购买
flexChain500.passRequest(3, false, 300); // 没有优惠券，普通购买
flexChain500.passRequest(3, false, 0); // 手机库存不足
flexChain500.passRequest(3, false, 300); // 没有优惠券，普通购买
```

### 1.10、模板方法模式

模板方法模式是一种只需使用**继承**就可以实现的非常简单的模式，说白了就是在父类（比如构造函数，class）中的原型中实现子类公共的方法，在子类中继承父类的方法，并且也可以此基础上重写某些方法或者添加子类独有的方法 。

```js
var Beverage = function () {}; // 饮料大类
Beverage.prototype.boilWater = function () {
    console.log('把水煮沸');
};
Beverage.prototype.brew = function () {}; // 空方法，应该由子类重写
Beverage.prototype.pourInCup = function () {}; // 空方法，应该由子类重写
Beverage.prototype.addCondiments = function () {}; // 空方法，应该由子类重写

// 模板方法，因为在这个方法里规定了子类究竟要执行哪些方法
Beverage.prototype.init = function () {
    this.boilWater();
    this.brew();
    this.pourInCup();
    this.addCondiments();
};

// 咖啡子类
var Coffee = function () {};
Coffee.prototype = new Beverage(); // 咖啡子类，继承父类的公共方法
// 在子类中具体实现
Coffee.prototype.brew = function () {
    console.log('用沸水冲泡咖啡');
};
//    同上
Coffee.prototype.pourInCup = function () {
    console.log('把咖啡倒进杯子');
}
// 具体实现
Coffee.prototype.addCondiments = function () {
    console.log('加糖和牛奶');
};
var Coffee = new Coffee();
Coffee.init();// 因为coffee本身没有定义init方法，所以实际上调用的是从父类继承过来的init方法

// 茶子类也是一样的
var Tea = function(){}; 
Tea.prototype = new Beverage(); 
Tea.prototype.brew = function(){ 
 console.log( '用沸水浸泡茶叶' ); 
}; 
Tea.prototype.pourInCup = function(){ 
 console.log( '把茶倒进杯子' ); 
}; 
Tea.prototype.addCondiments = function(){ 
 console.log( '加柠檬' ); 
}; 
var tea = new Tea(); 
tea.init();
```

### 1.11、享元模式

是一种**性能优化的设计模式**，简单来说就是找到**大量对象中公共的属性将其抽离出来作为共享对象**，然后剩下的的属性作为外部属性；然后再进行组合形成完整的对象，可以大大减少对象数量，虽然组装起来比较麻烦，但相对来说还是值得的。

享元模式的**关键是如何区分内部状态和外部状态**，那么它们分别有啥特点呢？

1.  内部状态存储于对象内部。
2.  内部状态可以被一些对象共享。
3.  内部状态独立于具体的场景，通常不会改变。
4.  外部状态取决于具体的场景，并根据场景而变化，外部状态不能被共享。

**啥时候使用？**

1.  一个程序中使用了大量的相似对象。
2.  由于使用了大量对象，造成很大的内存开销。
3.  对象的大多数状态都可以变为外部状态。
4.  剥离出对象的外部状态之后，可以用相对较少的共享对象取代大量对象。

就像《JavaScript设计模式》举得例子，原来模特的构造函数时这样的：

```js
var Model = function(sex,underwear) {
  this.sex = sex;
  this.underwear = underwear
}
```

很明显模特的性别是共享属性（因为即便是再多的衣服性别永远都是男女），所以要以性别作为共享对象：

```js
var Model = function(sex,underwear) {
  this.sex = sex;
}
```

### 1.12、中介者模式

主要是为了降低对象间耦合性而存在的一种设计模式，最直观的：

![image.png](https://cdn.nlark.com/yuque/0/2022/png/1528528/1650701826593-6e37863b-f79d-48cc-a570-6a7969e8434b.png)

中介者模式的作用就是**解除对象与对象之间的紧耦合关系**。增加一个中介者对象后，所有的 相关对象都通过中介者对象来通信 。

![image.png](https://cdn.nlark.com/yuque/0/2022/png/1528528/1650701877783-d1185d10-6ed4-46a9-87a1-3c3565ef30b3.png)

**优点**：解除对象与对象之间的紧耦合关系，由原来的多对多变成多对一。

**缺点：** 系统中会新增一个中介者对象 ，这个对象要和多个对象间通信，所以往往这个对象很复杂，也难以维护。

### 1.13、装饰者模式

能够在不改变对象自身的基础上 ，可以动态地给某个对象添加一些额外的职责（有点像按需加载的意思）。

### 1.14、适配器模式

**定义**：是解决两个软件实体间的接口不兼容的问题（就像生活中的转接头一样，不需要改变两套软件本身，只需转接一下就行了）。

> 其实这种方式在开发中很普遍，比如后台返回的接口数据不是我们想要的格式，我们一般就会定义一个函数将其转化为我们想要的，这也是在使用适配器模式呀！

```js
let googleMap = {
  show() {
    console.log("渲染谷歌地图");
  },
};
let baiduMap = {
  show() {
    console.log("渲染百度地图");
  },
};

function renderMap(map) {
  if (map.show instanceof Function) {
    map.show();
  }
}
// 现在有了第三方库，里面有这么一个对象
let appleMap = {
  display() {
    console.log("渲染苹果地图");
  },
};

//对于第三方库我们最好不要改源码，但我们可以定义一个适配器，让其变成我们想要的样子
let _appleMap = {
  show() {
    appleMap.display();
  },
};

renderMap(googleMap); // 渲染谷歌地图
renderMap(baiduMap); //渲染百度地图
renderMap(_appleMap); //渲染苹果地图

```

### 1.15、状态模式

状态模式的**关键**是把事物的 每种**状态都封装成单独的类**，跟此种状态有关的行为都被封装在这个类的内部。还是以开关电灯为例：默认电灯是关闭状态，按一下是弱光，按第二下是强光，按第三下关闭灯光，即：

![image.png](https://cdn.nlark.com/yuque/0/2022/png/1528528/1650717158513-50759270-9c18-4e0b-b314-9169c0bea561.png)

  

​  

一般的写法肯定是封装一个函数，然后里面是各种`if-else`，通过判断电灯的状态来执行不同的操作，这种代码也行，但是维护性不好——如果将来新增其他状态呢，如果利用状态模式就比较合适：

```js
// 每种状态都封装成单独的类，跟此种状态有关的行为都被封装在这个类的内部，三种状态，封装了三个状态类，各自的行为在他们的原型上
// OffLightState：
var OffLightState = function (light) {
  this.light = light;
};
OffLightState.prototype.buttonWasPressed = function () {
  console.log("弱光"); // offLightState 对应的行为
  this.light.setState(this.light.weakLightState); //改变状态 切换状态到 weakLightState
};

// WeakLightState：
var WeakLightState = function (light) {
  this.light = light;
};
WeakLightState.prototype.buttonWasPressed = function () {
  console.log("强光"); // weakLightState 对应的行为
  this.light.setState(this.light.strongLightState); // 切换状态到 strongLightState
};

// StrongLightState：
var StrongLightState = function (light) {
  this.light = light;
};
StrongLightState.prototype.buttonWasPressed = function () {
  console.log("关灯"); // strongLightState 对应的行为
  this.light.setState(this.light.offLightState); // 改变状态 切换状态到 offLightState
};

```

电灯类

```js
// 电灯类
var Light = function () {
  // 在电灯内部就初始化好三种状态类，因为他们是电灯内置的三种状态
  this.offLightState = new OffLightState(this);
  this.weakLightState = new WeakLightState(this);
  this.strongLightState = new StrongLightState(this);
  this.button = null;
};

// 初始化电灯是offLightState（灭者的）
Light.prototype.init = function () {
  var button = document.createElement("button"),
    self = this;
  this.button = document.body.appendChild(button);
  this.button.innerHTML = "开关";
  this.currState = this.offLightState; // 设置当前状态
  this.button.onclick = function () {
    self.currState.buttonWasPressed();
  };
};

// 改变状态的公共方法
Light.prototype.setState = function (newState) {
  this.currState = newState;
};

// 执行实例化
let light = new Light();
light.init();

```

**优点**

1.  状态模式定义了状态与行为之间的关系，并将它们封装在一个类里。通过增加新的状态 类，很容易增加新的状态和转换。
2.  用对象代替字符串来记录当前状态，使得状态的切换更加一目了然。

**缺点**

会在系统中定义许多状态类 ，系统中会新增不少对象，逻辑比较分散（至少没使用`if-else`来的清晰）

**和策略模式的关系**

**相同点：** 它们都有一个上下文、一些策略或者状态类，上下文把请求委托给这些类来执行 。

**不同点：**

1.  策略模式中的各个策略类之间是平等又平行的，它们之间没有任何联系。
2.  状态模式中，状态和状态对应的行为是早已被封装好的，状态之间切换有逻辑性。

## 二、设计原则

### 2.1、单一职责

**定义**：就是一个对象（方法）只做一件事。

**优点**：降低了单个对象或方法的复杂度。

**缺点**：增加编写代码的复杂度。

**难点**：如何正确的分离职责。

### 2.2、最少知识原则

**定义**：在设计程序时，应当尽量减少对象（ 系统、类、模块、函数、变量 ）之间的交互

**用途**：中介者模式、封装函数、局部变量

### 2.3、开放-封闭原则（重点 ）

**意义**： 几乎所有的设计模式都是遵守开放-封闭原则的，我们见到的好设计，通常都经得起开放封闭原则的考验

**定义**： 当需要改变一个程序的功能或者给这个程序增加新功 能的时候，可以使用增加代码的方式，但是不允许改动程序的源代码。

**用途**：每当我们看到一大片的 if 或者 swtich-case 语句时，第一时间就应该考虑，能否利用对象的多态性来重构它们 ， 利用多态的思想，我们把程序中**不变的部分隔离出来**（动物都会叫），然后把**可变的部分封 装起来（不同类型的动物发出不同的叫声），**总之**，** 挑选出最容易发生变化的地方，然后构造抽象来封闭这些变化

```js
// 不变的部分，每个动物都会叫
var makeSound = function( animal ){ 
 animal.sound(); 
};
// 变化部分，不同动物叫声不一样
var Duck = function(){}; 
Duck.prototype.sound = function(){ 
 console.log( '嘎嘎嘎' ); 
}; 
var Chicken = function(){}; 
Chicken.prototype.sound = function(){ 
 console.log( '咯咯咯' ); 
}; 
makeSound( new Duck() ); // 嘎嘎嘎
makeSound( new Chicken() ); // 咯咯咯
```

## 三、总结

**将不变的部分和变化的部分隔开**是每个设计模式的主题，所以在针对某个问题而言，如果想使用某个设计模式，最基本的工作是**找到变化的部分和不变的部分，并分割开。**

## 四、小感悟

1.  如果一段代码中有太多的`if-else`，就要考虑用设计模式了，所谓可维护的代码就是一定不是那种各种`if-else`的代码
2.  设计模式遵循开放-封闭原则，目前看来就是尽可能少改动代码，尽量降低耦合性（比如函数和函数间的，逻辑和逻辑间的）

## 五、代码重构

1.  尽量不要出现复杂的函数，如果一个函数代码过长，就要考虑是不是可以摘出来一部分。
2.  `if-else`语句中重复出现的代码，要将其摘出来，放在判断之外。
3.  尽量不要出现嵌套的`if-else`，可以将内部嵌套的部分封装成函数，这样也更容易阅读。
4.  尽量减少函数的参数数量，可以采用传入对象的方式进行替换。
5.  三元运算符，一般只用在简单的判断上，如果有多个判断还是用if-else吧：

```js

 b === doc ? 1 :

 0; 
} 
```

是不是很难理清逻辑，如果使用if-else就好很多吧！

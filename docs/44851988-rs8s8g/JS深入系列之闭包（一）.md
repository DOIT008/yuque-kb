## 什么是闭包

在《你不知道的javaScript上》是这样定义的：

> 当函数可以记住并访问所在的词法作用域时，就产生了闭包，即使函数是在当前词法作用域之外执行（要记得词法作用域，包括作用域链在函数定义的时候已经确定了）。

其实闭包无处不在，在我们写的程序中，每一个函数都是一个闭包，因为其都可以访问全局变量，也就是全局的词法作用域

就是有权访问另一个函数内部变量的函数，举个例子

## 代码示例

```js
function foo(){
    var a = 12;
    function bar (){
        console.log(a)
    }
    return bar
}
var bar1 = foo()
bar1()
```

  

为什么闭包如此神奇？明明父函数 `foo` 已经执行完毕了，并且父函数的执行上下文已经从执行栈中弹出，为什么内部的 `bar` 函数依然能够访问 `foo` 函数中的变量呢？

**其实这跟函数从创建到执行的机制有关：**

当一个函数创建的时候，会首先创建一个全局的执行上下文对象，这个对象里包含三个属性：

1.  this
2.  变量对象vo
3.  作用域链

对于上面的代码而言，当函数foo创建的时侯(还未执行)，其执行上下文是：

```js
ESObj = {
	this:{...},
  vo:{
  	arguments:{
    	length:0
    },
    a:undefined,
    bar:function(){..}
  },
  scopeChain:[globalContext.vo]
}
```

当准备开始执行的时候，就会把上一步的 `vo` 放到作用域链的前部，其执行上下文是：

```js
ESObj = {
	this:window,
  vo:{
  	arguments:{
    	length:0
    },
    a:12,
    bar:function(){..}
  },
  scopeChain:[ESObj.vo,globalContext.vo]
}
```

`foo` 代码执行完毕，开始执行 `bar1` （还未执行），同样的还是会创建执行上下文，如下所示：

```js
ESObj = {
	this:{...},
  vo:{
  	arguments:{
    	length:0
    },
  },
  scopeChain:[ESObj.vo,globalContext.vo]
}
```

同样的，当 `bar1` 准备执行的时候，和 `foo` 函数一样，会把自己的变量对象vo置于作用域链的前方：

```js
ESObj = {
	this:{...},
  vo:{
  	arguments:{
    	length:0
    },
  },
  scopeChain:[ESObj.vo,ESObjFoo.vo,globalContext.vo],
}
```

  

**虽然当** `**foo**` **函数执行完毕后，其上下文从执行栈中已经弹出来了，**

**按照道理来说** `**foo**` **执行完毕后会把** `**foo**` **内部的变量等所占据的内存空间释放掉，但是因为闭包的存在并没有回收，**

**为什么？**

**因为变量**`**bar1**`还保存着对`foo`内部函数(`bar`)的引用呢；而在`bar`内部还使用着变量`a`呢，并不满足回收的条件**，****所以javascript依然会把** `**foo**` **的变量对象保存在内存中，所以** `**bar1**` **依然能够通过作用域链访问到** `**foo**` **的变量对象。因为** `**bar**` 函数就在 `foo` 函数内部呀**，所以作用域链已确定了，因为它是通过作用域链访问到的！**

  

## 再来一个栗子

for循环和闭包

```js
for (var i=1; i<=5; i++) {
(function() {
var j = i;
setTimeout( function timer() {
console.log( j );
}, j*1000 );
})();
}
```

上面能打印出什么？很显然是1，2，3，4，5为什么呢？

这就是闭包的威力，当 `i=1`  的时候，通过一个自运行的函数用 `j` 将当前的i保存了起来，此时 `j=1` ，虽然根据事件循环机制，当循环结束后才执行 `timeout` ，但是此时 `timer` 寻找 `j` 的时候是从那个自运行函数里面找到的，你可能会说，自运行函数并不是已经执行完毕了嘛？**解释的话还是那句--其实j并没有回收，因为有timer函数引用着呢，也就是说自运行函数本身就是个闭包，他存在的意义是创建了一个封闭的作用域**

## 闭包的缺点

我们知道代码中的变量是存储在内存中的，一般来说一个函数执行完毕后，其内部的局部变量会被垃圾回收掉，但是由于闭包的存在会导致，某些变量不会被回收，所以容易造成内存泄漏。

## 总结

说白了，**闭包的产生并不是在函数运行时产生的，在定义的时候就产生了，**只要满足这个定义的条件--**在内部函数中访问了外部函数定义的局部变量**，虽然外部函数执行完了，但只要内部函数保持着对变量的引用，js引擎的垃圾回收机制就不会将作用域回收（至少这个变量不会被回收），依然保存在内存中，然后内部的函数就可以通过作用域链来访问这个外部函数的作用域了，无论何时无论在哪儿。

还有就是如果把全局当作一个特殊的函数，其实我们写的每一个函数都是一个闭包，因为在全局定义的函数能够访问全局的变量，虽然全局执行完了，但并没有释放掉内存，因为内部有各种各样的函数保持着对变量的引用呢

## 补充理解

要想彻底理解闭包，就要彻底弄清楚一个函数在执行的时候到底发生了什么。

> “一个函数自执行之前会初始化一个执行环境以及自己的作用域链(当然在定义的时候已经被定义好了)，使用arguments和其他命名参数的值初始化函数的活动对象”这里的活动对象可以认为是包含作用域链中各种变量的一个对象

——摘自《JavaScript高级程序设计》

一般而言，一个函数执行完毕后其内部的变量对象和自己的作用域链会随之被销毁，但对于闭包而言就不同了，外层函数在执完毕后，它的作用域被包含在内部函数的作用链中（其实在写这个函数的时候已经确定好了），而且它的变量对象也不会被销毁，因为内部函数有对其的引用(内部函数用着其变量对象其中的值，也就是某个变量，所以外部函数变量对象不会被销毁)，这也就为什么返回内部函数的函数不一定是闭包的原因。

  

## 总之

闭包是一个非常强大的特性，但人们对其也有诸多误解。一种耸人听闻的说法是闭包会造成内存泄露，所以要尽量减少闭包的使用。

局部变量本来应该在函数退出的时候被解除引用，但如果局部变量被封闭在闭包形成的环境中，那么这个局部变量就能一直生存下去。从这个意义上看，闭包的确会使一些数据无法被及时销毁。使用闭包的一部分原因是我们选择主动把一些变量封闭在闭包中，因为可能在以后还需要使用这些变量，把这些变量放在闭包中和放在全局作用域，对内存方面的影响是一致的，**这里并不能说成是内存泄露。如果在将来需要回收这些变量，我们可以手动把这些变量设为 null。**
